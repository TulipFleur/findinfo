## 2. 当前实际工作流

```text
解析 CLI、加载 core/config
  -> entity（有 --name 时）
  -> onepass（未关闭时）
  -> certs -> subs
  -> brute（主动且启用）
  -> icp（有备案码且未关闭）
  -> 多轮：
       DNS -> probe -> ipagg -> ports/vhost -> crawl -> extract
       -> 从共享资产图补入 run membership
       -> 比较域数量和新旧队列，决定继续或停止
  -> 汇总 coverage / verdict
  -> status / wait / brief / report
```

主流程仍由手工计划和手工调用驱动。StageRegistry 已存在，但没有成为生产调度的唯一来源。新增 work queue 目前主要接入 DNS，extract 仍由旧队列处理。

## 3. 已确认的主要问题

### F01 — P1：JS 新队列入队后没有消费者

位置：`findinfo.py:2267`、`lib/work.py:345`、`lib/tools.py:2156`、`findinfo.py:2483`。

extract 后将全部输入 URL 交给 `adopt_js_backlog`，包括 HTML 和已经完成的 JS；这些 URL 成为新队列中的 extract/pending。实际抓取仍消费旧 `js_queue`，生产中的 `work.claim/work.finish` 只用于 DNS。最终判定又读取新队列 outstanding，因此成功处理后的工作仍阻止收敛。

离线复现：旧队列的 bundle.js 已 done；adopt 首页 HTML 和 bundle.js 后，新队列出现两项 extract/pending，outstanding=2。

修复要求：确立一个可领取的 JS 工作状态源，完成后原子确认对应任务；HTML 不能当作未处理 JS 入队。验收必须包含“成功处理后队列归零”。

### F02 — P1：DNS 暂态失败可能最终返回 complete

位置：`lib/tools.py:1149`、`findinfo.py:2074`、`findinfo.py:958`、`findinfo.py:2105`、`findinfo.py:2343`。

DNS 可返回 `ok=True, transient>0`。阶段投影没有把暂态状态转为 partial，默认 outcome 又被补成 OK。主流程不按逐域解析结果确认任务，而将领取的 DNS 工作统一以成功确认。域数量不增长、队列归零后便提前收敛。

真实函数 AST 与内存桩复现：输入 `ok=True, count=0, transient=1`，产生 `status=succeeded`、checkpoint=done，最终为 `complete/no_new_assets/rc=0`。

修复要求：逐域确认，暂态项保留可重试状态；最终判定读取未完成义务，不能仅依赖域数量稳定。

### F03 — P1：DoH 成功结果不进入 probe

位置：`lib/tools.py:1128`、`findinfo.py:994`、`findinfo.py:2040`。

DoH 以 source=doh 写入资产，`_DNS_SOURCES` 却没有 doh。DNS 运行后仍通过该来源集合重建 probe 输入，导致新鲜 DoH 成功域被遗漏。历史 dnsx 来源域即使当前解析状态为 NXDOMAIN，反而仍可能保留在输入中。

离线复现：新域仅有 doh 来源时，`dns_resumed()` 返回 `resolved=0, hosts=[]`。

修复要求：按当前 run 的有效解析状态和证据构建输入，兼容所有 resolver 路径，并排除当前不可用状态。

### F04 — P1：过期 running 租约不能重新领取

位置：`lib/work.py:232`。

claim 只查询 pending/failed，排除了已经进入 running 的工作；lease_expiry 条件因而无法回收崩溃 worker 的 running 项。同一查询也未检查 retry_at，退避时间不起作用。

内存 SQLite 复现：首次 claim=1，16 分钟后重新 claim=0，仍有 running=1/outstanding=1；另一失败项设置 60 秒后重试，却在第 1 秒被重新领取。

修复要求：原子回收过期运行项，校验 retry_at，并使旧 lease token 不能确认新所有者的结果。

### F05 — P1：fencing 检查与写入不原子，流水线仍绕过检查

位置：`lib/jobs.py:556`、`lib/jobs.py:559`、`findinfo.py:832`、`findinfo.py:1347`。

`fenced_write` 在锁外读 token，之后才进入 update_state 的锁；恢复切换 token 可以发生在两者之间。流水线 `_write_status` 还直接调用 update_state，未携带 fence。首次启动也没有生成 token，会进入 legacy 兼容分支。

确定性交错复现：旧调用取得旧快照后，新 attempt 写入新 token；旧 fenced_write 仍返回 True，并把新状态覆盖为 completed。

修复要求：所有受保护状态写入在同一锁内完成 token 比较和更新；首次启动也生成 token。对派发与确认使用同一所有权约束，明确已在途操作的处理方式。

### F06 — P1 条件风险：实体资产对应关系丢失，可能扩大主动范围

位置：`lib/tools.py:391`、`lib/tools.py:411`、`lib/tools.py:425`、`findinfo.py:1803`、`findinfo.py:1896`。

ENScan 先将多个实体的公司、域名和备案记录分别 flatten，只过滤公司名称，随后把全部域名挂到第一个保留公司。若返回内容确实含未获准实体的资产，这些域名可能进入目标种子和主动范围。新增身份门禁发生在落库之后，不能恢复已丢失的实体归属。未验证真实 ENScan 响应，因此不能说当前美团采集已经串目标；如果输出全属已认可集团主体，合并也可能合法。

修复要求：按实体对象保留并过滤其资产集合，建立稳定主体引用；所有权没有证据的资产只作为相关证据保存。

### F07 — P1：新 run 静默吸收历史同后缀资产

位置：`findinfo.py:1031`、`findinfo.py:2307`、`findinfo.py:2364`、`findinfo.py:2440`。

每轮无条件扫描共享图的全部 scope 域并附入当前 run，使用 pipeline 作为 producer/upstream，并写当前观察时间。这不是有原始证据引用的显式复用。最终部分 counts/endpoints 和 JS backlog 也仍采用全库统计，可受到其他运行影响。

离线复现：历史 `historic.mt-a.example.com` 在没有本轮观测的情况下成为新 run 成员，同时新增一条当前时间的 pipeline observation。

修复要求：采集写入时原子记录 run membership；缓存复用保留原 upstream、observed_at 并记录 attached_at；各 run 的视图和待处理统计读取自己的成员。

### F08 — P1 设计缺口：计费审计不等同请求前控制

位置：`lib/tools.py:873`、`lib/metered.py:90`、`findinfo.py:1958`、`lib/tools.py:2409`。

provider 调用后才记录 JSONL；没有并发 claim、预算预留、累计重试上限、分页复用或 uncertain 状态。这未满足原设计的预算控制目标，不等于已经发生错误收费。`_seen` 会丢弃相同 key/状态的第二次 record，但正常主流程是否能重复到该记录路径尚未证实，当前仅作为接口契约缺陷。quota block 主要在汇总时读取，未普遍阻止下一次派发。现有 mapping_wait 提供进程内速率限制，应与预算控制区别。

onepass 的源码默认选择有凭据的来源，来源表包含 FOFA/Quake/Hunter；此路径不接收 ledger。只有实际二进制与该源码一致且相应凭据可用时才可能调用这些来源。未验证原生工具版本、账户套餐或实际费用。uncover 当前记录的是原生派发次数，也不能直接解释为精确上游 HTTP 次数。

修复要求：请求前领取唯一请求、预留预算，保留独立 attempt/request ID；可能已经计费的失败进入 uncertain。隐藏收费路径必须排除或显式受控，不能仅在请求后汇总。

### F09 — P2：dry-run/offline 的启动链仍有配置读取和目录副作用

位置：`findinfo.py:107`、`lib/core.py:124`、`lib/core.py:431`。

解析离线开关前已经导入 core/tools，执行目录创建和 load_config；后者会读取实际 config.json、.env。doctor_offline 函数自身不联网，但入口不满足“不读凭据、无副作用”的约定。

隔离副本实际 CLI 复现：对一个不存在的 home 执行 dry-run，返回 rc=0，同时创建 cache、runs 目录。本轮没有将实际凭据放入副本，也没有读取原配置。

修复要求：离线规划和解析使用纯 bootstrap，运行时配置与采集模块延迟加载。

## 6. 建议修复顺序

1. 修复 DNS 暂态判定、逐域确认和 DoH 到 probe 输入；先消除错误 complete。
2. 统一 JS 工作状态，回收过期租约，完成“入队—处理—确认—恢复—归零”的闭环。
3. 保留逐实体资产归属，改为 subject ID 选种子；收紧 run membership 和观测时间语义。

5. 补齐收费请求前控制和 onepass 来源边界，再实现刷新、分页和累计重试策略。
6. 修复真实 stdout 字节边界、纯离线 bootstrap 和 RunSpec 边界值，最后同步文档及完成标记。

每项都应增加实际 cmd_run/CLI 路径的反例测试，使用原始合成 provider/tool 输出，避免只调用新增 helper。尤其要验证暂态失败不完成、成功 JS 不残留、过期租约可恢复、DoH 成功进入主动验证，以及被拒主体的资产不进入范围。
